# Jira Issue 类型与层级约定

状态：已评审通过，2026-11-19 并入 Confluence [OMR 项目管理原则](https://bamboolab.atlassian.net/wiki/spaces/OMR/pages/589827) v1.0 与 [OMR 项目管理速查](https://bamboolab.atlassian.net/wiki/spaces/OMR/pages/622593)。本文保留为实施记录；规则以 Confluence 为准。

适用范围：OMR 项目的版本规划、Epic、Story、Task、Subtask 与 Spike。

## 1. 目的

Task 描述只承诺“交付什么”，不承载“怎么做”。技术路线变化时，优先更新设计文档与 Subtask；只有交付目标或范围变化时才改 Task。这样避免 Task 描述随着模块名、接口名、状态机拆分反复重写。

## 2. Issue 类型

Jira 的 Issue Type 语义由团队约定，不由工具强制。本项目按以下含义使用。

| 类型 | 回答的问题 | 主要内容 | 典型对象 |
| --- | --- | --- | --- |
| Epic | 为什么做、版本目标是什么 | 目标、成功标准、范围/非范围 | 一个版本或一条完整能力线 |
| Story | 对外部使用者有什么可感知价值 | 可演示的价值切片、验收标准 | 现场操作、下游开发者可观察的能力 |
| Task | 这个里程碑或使能工作交付什么 | 意图、范围、验收标准、依赖 | 对象层、构建基线、工具、重构 |
| Spike | 需要先决定什么 | 问题、时间盒、输出 | 技术路线调研、接口选型 |
| Subtask | 具体下一步做什么 | 一个可独立验收的工作单元 | Story 或 Task 下的实现、验证、文档 |
| Bug | 什么行为不符合预期 | 复现、期望、实际、影响 | 缺陷修复 |

Story 和 Task 是同级工作项，都可以挂 Subtask。Subtask 不能独立于父项存在，也应有自己的验收方式。

## 3. 判定规则

按顺序判断：

1. 版本级目标或完整能力线 → Epic。
2. 有明确外部使用者、可演示、可独立验收的价值切片 → Story。
3. 内部使能、里程碑、构建/工具/重构 → Task。
4. Story 或 Task 下可独立标记完成的工作单元 → Subtask。
5. 需要先做技术决策、输出是结论而不是可运行产物 → Spike。
6. 行为不符合预期 → Bug。

Story 与 Task 的边界看“外部价值”，不看工作量。一个很大的技术里程碑仍是 Task；一个很小的外部能力也可以是 Story。不要用 Story 作为“大 Task”的同义词。

## 4. 描述模板

### Task

```markdown
## 意图
任务完成后，系统具备什么能力。

## 范围
- 包含：
- 不包含：

## 验收标准
可观察、可验证的结果，不写实现方式。

## 依赖与风险
前置任务、外部依赖、已知风险。

## 设计锚点
链接到设计文档、ADR 或相关 Issue；不在此复述设计。
```

### Story

```markdown
## 使用者与场景
谁，在什么场景下，需要什么。

## 价值
为什么需要这个能力。

## 验收标准
可演示、可验收的行为。

## 非范围
明确不包含的相邻能力。

## 设计锚点
链接到设计文档；不在此写实现细节。
```

### Subtask

```markdown
## 交付
一个可独立完成、可独立验收的产物。

## 验收方式
host 测试 / 目标构建 / 真机验证 / 文档评审。

## 依赖
前置 Subtask 或外部条件。

## 说明
需要时链接设计文档或评论，不在此写完整设计。
```

### Spike

```markdown
## 问题
需要回答的技术问题。

## 时间盒
最长投入与截止时间。

## 输出
决策记录、ADR、设计文档或原型结论。

## 影响
结论会影响哪些 Task / Subtask。
```

## 5. 内容边界

Jira 中保留：

- 意图、范围、非范围；
- 验收标准与验证方式；
- 依赖、风险、阻塞；
- 设计锚点链接；
- 影响交付的决策结论。

设计文档中保留：

- 架构、接口、数据模型；
- 文件路径、模块名、函数名；
- 状态机、时序、失败路径；
- 测试矩阵与实现细节。

评论中保留：

- 技术路线演进记录；
- 评审结论与证据；
- 被替代方案的说明。

原则：Task 描述是交付承诺，Subtask 是工作单元，设计文档才是技术事实源。

## 6. 变更管理

1. 技术路线变化：更新设计文档与受影响的 Subtask；Task 描述不变。
2. 交付目标或范围变化：更新 Task 描述，并留评论说明原因。
3. 已关闭 Issue 不重写；需要新范围时新建 Issue 并链接旧 Issue。
4. 设计细节变化写入评论或设计文档，不反复重写描述。
5. Subtask 增删是正常规划行为；Task 的意图应保持稳定。

## 8. 反例

- Task 描述列出会被替换的模块名、接口名或状态机步骤。
- 用描述维护技术设计，技术路线一变就需要整篇重写。
- 把每个文件修改或每次提交拆成 Subtask。
- 用 Story 表示“很大的 Task”，但没有外部使用者和可演示价值。
- 把关键技术决策藏在 Task 描述里，没有设计文档或评论记录。
- Subtask 没有验收方式，只写“实现某模块”。

## 9. 迁移清单

1. 将进行中的 Task 描述收敛到意图、范围、验收标准、依赖、设计锚点。
2. 把原有实现细节移入设计文档或 Task 评论。
3. 为进行中的 Task 补建 Subtask，按可独立验收的产物拆分。
4. 技术设计未定时先建 Spike，再建实现 Subtask。
5. 后续技术路线变化只更新设计文档和受影响 Subtask，不改 Task 意图。
