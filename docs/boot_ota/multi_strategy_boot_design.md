## 1. 设计目标

**一个 boot 系统，一套决策骨架，支持多种"提交策略"**：

- 提交策略 = 启动时把"待升级镜像变为运行镜像"的动作差异（overwrite / swap / direct-xip / ram-load）。
- 策略由**构建/配置期固定**为 bootloader binary 的单一行为（K-11：运行时不做策略切换——bootloader 薄且确定性）。
- 决策骨架（读 meta → 判状态 → 校验 → 提交 → 启动 → 确认/回退）与提交策略**正交**：换策略不换骨架，换骨架部件不换策略。

参考：MCUboot 以同一镜像格式 + 构建期开关（swap / overwrite / direct-xip / ram-load）支撑全部模式——策略差异被收敛在"提交动作"，而不是整个启动路径分叉。

### 1.1 设计锚点（2026-09-18，本方向的基准约束）

> 本节是**用户拍板的方向性锚点**，层级高于本文件其他章节的推导；后续任何设计不得与之冲突，冲突时回改设计而不是回改锚点。

**A. 策略集合与优先级**

| 档位 | 策略 | 含义 |
|---|---|---|
| **承诺（首版必须支持）** | **Direct-XIP**（首选）、**Swap-using-offset**（次之） | 架构必须为二者留出完整的实现位置 |
| 演进（架构不变，动作后补） | **RAM-Load**、**Overwrite** | 只作为骨架的验证面，不阻塞首版 |

落地顺序：**Direct-XIP → Swap-using-offset → RAM-Load**（Overwrite 随演进档）。

**B. 交集原则（本次架构的总原则）**

> 在三个（乃至四个）策略之中找**可复用的交集核心**；**无法复用、没有交集的部分则提升层级，将变化与核心解耦**。

即：换策略时应当只替换**高层的变化点实现 + 配置**，核心代码零改动。交集边界的具体划分见 §3.7，其接口投影见 §3.8。

**C. 三层约束（几何约束的落地方式，与 B 同源）**

> 几何约束靠 **工具校验 + 编译器策略约束 + 运行时防御** 三层承担，同样是"把变化提升层级"。

| 层 | 手段 | 时机 |
|---|---|---|
| 工具 | `omimg` 等构建期工具的容量/几何校验（K-40） | 构建期 |
| 编译器 | 布局表是**编译期常量** → 策略级约束用 `_Static_assert` 拦下 | 编译期 |
| 运行时 | 决策核的防御性判定（注册期几何校验 + 决策期失效判据） | 运行期 |

一句话：**不同策略，同一骨架。**

## 2. 术语

| 词 | 含义 |
|---|---|
| 槽（slot） | 一个可容纳完整镜像的**逻辑启动位置**（如 primary/secondary，或 A/B）。槽是逻辑概念 |
| 介质 | 槽的物理承载（片内 flash、外部 SPI flash……）。介质映射是板适配职责（P-04） |
| 镜像（image） | 自描述二进制：头部契约 + 负载（可选尾部摘要区，K-09） |
| meta | 记录 boot 决策状态的小块存储（K-05：双份轮转 + seq + magic + CRC） |
| 指针 | meta 中"当前应启动哪个槽"的引用（K-04：激活 = 翻指针，不是搬移） |
| pending / confirm / rollback | 状态语义三件套（K-07/K-08）：试一次 / 正式永久 / 回退 |
| 后门（backdoor） | bootloader 里的**接收通道 + 门禁**（进入判据 + 命令面）——是一个"**入口**"，不是一个"**用途**"（K-12/K-21/Q-16） |
| 救援会话（recovery session） | **后门内的会话运行态**（上下文 B）。同一通道承载三种语境：**正常升级**（G2）／**救援**（G1，无有效镜像等）／**维护诊断** |
| 进入窗口 | 引导期（A）末尾用于判定"是否进后门"的时间窗/条件——即"boot 等待救援模式"所指的那段状态 |

## 3. 策略无关的固定骨架

### 3.1 镜像头契约（K-09，第一交付物）

最小字段集：magic、**结构版本号**、镜像总长、负载起始偏移（对齐用，解决"槽首部与写对齐错位"——MCUboot image offset 思想）、flags、预留区。头自身带强校验；**头外全部负载**的完整性在激活前完成校验（K-09）。

> 契约是 bootloader 与 app **两个独立 binary 间的 ABI**：复位向量偏移、保留区大小、头布局、meta 布局、确认入口的调用约定，全部由此契约约束并版本化。契约改变必须显式升版本号，旧侧遇新侧结构必须能**优雅拒绝**而非误读。

### 3.2 槽位视图

- 上层只表达"槽 + 指针"（P-04）。
- 槽 → 介质 + 基址的映射由每板 bootloader 适配提供；remap / bank 切换 / VTOR 处理全部在适配内（P-04）。
- **架构策略无关 / 布局表策略相关**（2026-09-16 记录）：分区表每行自带介质名（`devName`），故"两槽位于**不同介质**"在架构上天然可表达（片内 / 片外 / 一片一片内皆可），决策核只认**分区名**、代码中不出现地址与介质。**策略相关的是槽的数量/形状/大小**——direct-xip = A/B 等大且**均可 XIP**；swap = A/B 等大 +（可选）scratch 区；overwrite = 运行槽 + staging 区；ram-load = 非 XIP 槽 + RAM 目标——这些差异落在**工程配置的布局表**（bootcfg）里，不进框架代码。即：换策略换的是**配置**，不是架构。
- **注意（待调研）**：对拷类策略（swap）若两槽**跨介质**，会引入"跨器件拷贝"的额外语义与耗时（两边擦除粒度也可能不同）——由板适配/策略实现承担，不是免费的；生态实际支持形态见专项调研（缺口清单 #22）。

### 3.3 boot meta（K-05）

- 独立于镜像的小区域；entry 结构：seq、状态字段（EMPTY / PENDING / VALID）、当前指针、回退计数、CRC。
- **双份（或三份）轮转 entry**：新状态写进空 entry（带更大 seq），旧 entry 延迟擦除；半写 entry 因 CRC 失败被忽略。
- 布局决策（份数/落点）见 Q-03；**entry 字段布局与写序见 Q-12**。

### 3.4 决策状态机（K-06：intent 先行、每步幂等）

```
上电 → 读 meta（取 CRC 有效且 seq 最大者）
  ├─ 状态=EMPTY            → 校验槽内当前镜像头 → 有效则按指针启动；无效 → 进后门（K-12）
  ├─ 状态=PENDING（试一次）→ 校验 staging 镜像（K-09）→ 执行提交策略（§4）→ 启动新槽
  │                         → 回退计数/窗口开始计时（K-08）
  │                         → app 自检通过后写 confirm → 下次按新指针跑 VALID
  │                         → 计数耗尽或窗口超时未确认 → 自动回退（各策略回退语义见 §4）
  └─ 状态=VALID            → 按指针启动对应槽
```

- 每步先写状态再动手；掉电后重启从 meta 判定"上次到哪、要不要续/退"，不依赖运行期记忆（K-06）。
- 确认语义：app 只能 confirm（或什么都不做），无权直接翻指针/改决策（K-07）。
- 跳转（启动）前的执行环境清理清单与**中断放开责任方见 Q-13**（清单与两案依据 K-32/K-33）。

### 3.5 权力分离（K-13）

| 动作 | 归属 |
|---|---|
| 写 staging 槽（流式写入新镜像） | 下载方：app 内 OTA 服务，或外部下载器经传输通道直写。**2026-09-18 收敛（首版）**：下载发生在**上下文 B（救援会话，同属引导侧）**——app 只发起（标 pending + 复位交棒），下载/擦写/提交全在引导侧完成（G1/G2，§3.6）；"app 内直写"是演进档 D |
| 标记 pending（"有新镜像待试"） | 下载方（写 meta 的 PENDING entry） |
| 校验、提交（翻指针/swap/overwrite）、回退判定 | **bootloader** |

据此，开工序列步骤 3（OTA 状态机）的边界自然划分：**app 侧 = 传输 + staging 写入 + 标 pending + 自检后 confirm**；**bootloader 侧 = 校验 + 提交 + 回退**。两半通过 meta 契约耦合，不共享代码路径。

> **2026-09-18 收敛**：首版把"传输 + staging 写入"整体划入**引导侧**（上下文 B）——app 侧只剩"**发起**（标 pending）+ 自检后 confirm"；上述划分仍然成立，只是首版的"下载方"= bootloader 自己（G1/G2，§3.6）。

### 3.6 上下文划分与目标（2026-09-18）

**决定一切的前提是"谁在跑"**——擦除合法性、链路归属、失败去向全部由它决定：

| | **A. 引导期**（boot path） | **B. 救援会话**（recovery session） | **C. 应用运行期** | **D. 应用内直写**（演进） |
|---|---|---|---|---|
| 执行者 | bootloader | **同一个 bootloader，停在会话循环** | app | app |
| 运行镜像 | 无（还没跳） | **无**（app 没在跑） | 在跑 | 在跑 |
| 可擦片内？ | ✅ | ✅ | ❌ | ❌（除非窗口已预擦 / 目标在外挂介质） |
| 链路归属 | bootloader（串口/CAN 可直接驱动） | bootloader | app（网络/WiFi 栈只有它有） | app |
| 时间预算 | 毫秒~秒 | 秒~分钟（受链路支配） | — | — |
| 失败去向 | → B 或停 | → 重来 / 换槽 | — | — |

**关键结构**：**A 与 B 是同一个 binary 的两个状态**（B 是 A 的一条分支），C 是另一个 binary，D 是 C 内部的一条路径。

> **术语澄清（2026-09-18）**：**"后门"与"救援"不是同一个东西**——**后门 = 通道/入口（+ 门禁）**，**救援 = 后门内的一种会话语境**。三者是一条链：
> `A 引导期末尾（进入窗口）→ [后门入口判据] → B 会话（同一 wire 承载三种语境）`
> 三种语境共用**同一套协议与命令组**，差别只在**入口判据**：G2 正常升级 = 被请求进入（app 标 pending + 复位）；G1 救援 = 无条件兜底进入（无有效镜像 / 窗口内握手）；维护诊断 = 同上通道、命令面按构建期裁剪（Q-16）。

**目标（首版）**：

| 编号 | 目标 | 含义 |
|---|---|---|
| **G1** | **兜底不可让步** | 设备任何时刻都有一个**不依赖 app** 的下载入口，两槽全坏也能灌写（R-DL-1）→ 要求 **B 存在** |
| **G2** | 正常升级 | app 发起 → **交棒**给 bootloader（首版 = 标 pending + 复位进 B）；下载、擦写、提交全在 B 内完成 |
| **G3** | 演进 | 只有 app 有链路的场景（WiFi/网络 OTA）→ **D 才有存在理由** |
| **G4** | 不变量 | 擦除不得与**同一片内 flash** 上的运行态并发（见 §3.10 修正③） |

**由此推出的首版结论**：**擦除时机问题在首版不存在二选一**——下载发生在 B（引导侧上下文），擦就在 **B 内按需擦**（合规、按需、零浪费；擦 bank2 时运行镜像在 bank1，跨 bank 连 stall 都没有）。**"预擦"只是 D 的入场券**，不是首版的选项。

### 3.7 交集核心的边界（2026-09-18）

**判据只有一条**：**换策略时，这一项是否必须改变？** 必须变 → 策略层；不变 → 核心。

**进核心（策略无关）**：

| 项 | 为什么与策略无关 |
|---|---|
| 镜像格式契约（结构、字段布局、判定顺序） | 三策略吃同一份镜像格式；只有个别字段的**启用与否**随策略变 |
| 校验核（摘要链、算法 ID、优雅拒绝） | 与"怎么提交"无关 |
| 槽位视图（槽 = 命名区域、按分区名取槽、代码不出现地址） | 布局的表达方式，不是策略的表达 |
| 决策数据的存储与维护（entry 读写、CRC+seq、预擦归属、引导期清理、稳态零写） | 三策略都要"记住上次到哪了"；擦除归属与策略无关 |
| 决策状态语义（EMPTY/PENDING/VALID/ABORTED、启动计数、确认、**回退判定**） | "试运行→确认→回退"是升级事务的通用语义 |
| 确认接口与权力分离（app 只能 confirm） | 通用（K-07/K-13） |
| **跳转执行器**（清理清单、VTOR、MSP、CONTROL、放开中断） | **清单完全相同，只有"跳去哪"不同** → 清单进核心，目标地址由策略给 |
| 下载/后门协议的**语义**（帧、命令组、ACK、幂等重传） | 协议与策略无关（K-21/K-25） |
| 失效判据与冷启动路径（镜像无效 → 不跳转 → 进后门） | 通用 |
| 失败模式矩阵的公共行 | 通用 |

**进策略层（变化点，提升层级后隔离）**：

| 项 | 为什么必须随策略变 |
|---|---|
| 槽的数量与角色 | 对称 A/B（direct）／primary+secondary（swap）／+staging（overwrite）／+RAM 目标（ram-load） |
| 几何要求 | XIP 能力（direct）／扇区均一 + 副槽 = 主槽 + 1 扇区（offset）／RAM 区不重叠（ram-load）→ 由**布局表 + 编译期断言**承载 |
| **提交动作** | 翻指针／逐扇区对调／拷入 RAM（ADR-0021 的"策略差异收敛在提交动作"） |
| **提交进度** | swap 必须持久化"换到第几扇区"（可跨启动）；direct/ram-load 不需要 → **核心给容器，策略给内容** |
| **回退动作** | 翻指针回去／继续完成或对调回去／重新拷旧镜像（**判定在核心，动作在策略**） |
| 下载写入的目标位置 | 非活动槽 + `payloadOffset`（direct）／**secondary 起点 + 1 扇区**（offset，K-41）／staging（overwrite）／非 XIP 槽（ram-load） |
| 镜像构建次数与链接基址 | direct = 两槽各构建一次；swap 与 ram-load = **一份镜像**（运行地址固定）→ 落在**工具链** |
| 字段校验的启用集 | `slotId`/`SLOT_BOUND` 校验是 **direct 特有**；ram-load 需要 RAM 标志位 |
| 策略特有的失效处理 | swap 中途掉电 = 断点续做/安全回退；ram-load 拷贝中断 = 重来 |

**一个必须点名的"半核心"项**：**`activeSlot`（当前该启动哪个槽）**——对 direct-xip 是核心信息；对 swap/ram-load，运行槽地址固定，该字段**退化为常量**。**决定：保留该字段**（核心 entry 的通用形状），策略不使用指针时其语义 = 运行槽，由策略解释——**不为了 swap 把核心 entry 结构分叉**。

### 3.8 四处缝（核心与策略的接口面）

边界画完后，核心与策略之间只剩四处缝——**换策略时只替换这四处的实现 + 布局表 + 构建配置，核心零改动**（§1.1-B 的可验证形式）：

| 缝 | 输入 | 输出 | 各策略实现 |
|---|---|---|---|
| **① committer（提交器）** | 待提交镜像位置 + 决策状态 | 完成／进行中（含进度落盘）／失败 | 翻指针 / 逐扇区对调 / 拷入 RAM |
| **② layout_policy（布局策略）** | 布局表 | 编译期断言集 + 运行期检查集 | 每策略一组要求（等大、XIP、扇区均一、RAM 区…） |
| **③ image_target（镜像落点）** | 目标槽 + 镜像 | **窗口描述符**（§3.9）+ 打包要求 | 非活动槽 / secondary+1 扇区 / staging / 非 XIP 槽 |
| **④ transfer_session（传输会话）** | 协议帧 + 窗口 | 已落盘偏移 + 前缀校验态 | **策略无关**（四项中唯一不随策略变的缝） |

落地方式：**单 binary 单策略**（K-11）——策略由构建期选择，四处缝以构建期绑定的实现进入 binary，不在运行期分发。

### 3.9 窗口描述符与续传点的传递面（2026-09-18）

**窗口描述符 = 布局表的投影**，不是新的事实源：

```
window = { dev, part, offset, capacity, align, erase_unit, verify_granularity }
```

| 策略 | 窗口取值 |
|---|---|
| direct-xip | `{片内, app_b, offset=0x200(payloadOffset), capacity=768K, align=4, erase=128K}` |
| swap-offset | `{片内, app_b(secondary), offset=+128K（第 2 扇区起，K-41）, capacity=768K, align=4, erase=128K}` |
| ram-load（演进） | `{外挂 SPI NOR, staging, offset=0, capacity=器件容量, …}` |

- **可计算性**：`capacity` 不是可独立填的数，而是 `f(槽几何, 策略)`——swap 下 `capacity = (副槽扇区数 − 1) × 扇区大小`。这正是"工具按器件几何求解布局"演进项的第一个消费者。
- **同源**：固件与上位机**从同一张布局表各投影一份**——上位机要算写入偏移与续传点，固件要算窗口边界。
- **传输层只见窗口**：它**不知道策略**，只按窗口写。

**续传点（会话游标）的传递面**：

> **用户拍板（2026-09-18）：续传点的承载方式（`.noinit` RAM / 非易失存储）属配置、计算与布局层面的内容，对 boot 与 ota 应当无感。** 故续传点是一个**面**（抽象读写接口），实现可落在 noinit RAM（软复位保留）或非易失存储；boot/OTA 代码只见面、不见实现。

**续传规则（NOR 物理约束，K-42）**：

1. **回扫只能定位，不能验真**（镜像内无块级预期值）→ 一致性由"重发同块由设备比对"或终审整镜像摘要给；
2. **续传点必须向下取整到擦除单元**，该单元**重擦 + 整单元重收**（片内 128K / 外片 4K）——分段粒度 = **擦除单元**，不是传输块；
3. **块校验归传输协议层**（会话内有效、可丢弃），**不动镜像格式契约**；终审 = 整镜像摘要；
4. 会话游标默认 RAM（权威在上位机，K-42）；三条路径优先级 = **设备端游标 > 回扫 > 重传**。

### 3.11 后门协议的归属与分层（2026-09-19）

**归属**：后门协议**不是独立协议**——它是**通用命令服务的一个命令组**（K-21/Q-08 早已记为"通信/命令服务的裁剪前身"）。三层分离，**只有 ①② 会重复，且重复量可预算**：

| 层 | 内容 | bootloader 侧 | app 侧 | 是否重复 |
|---|---|---|---|---|
| **① 传输层** | 帧定界、CRC、ACK/重传、停等、超时 | 自实现（零 OSAL） | 通信服务 | 会（可预算） |
| **② 命令层** | 组 ID + 命令码 + 参数/响应编码 | 裁剪版（只带 boot 组） | 通信服务（全量） | 会（可预算） |
| **③ 业务层** | 命令实现（写 flash / 擦 / 跳转 / 读 meta） | bootloader 实现 | app 实现 | **不是重复**——不同命令的实现 |

③ 之下**已共享**（FlashDev 同一套 API，R-NFR-6；ADR-0022 已证明同一套原语可跨裸机/RTOS 宿主）。

**路线（已定 2026-09-19）**：

| 阶段 | 形态 |
|---|---|
| **首版 = B**（契约共享 + 两份运行时） | **线格式单头文件**（帧结构 + 组/命令编号集中登记表）为唯一事实源；bootloader 侧写**最小裁剪运行时**（只带 boot 组、零 OSAL、停等、无动态内存）；**app 侧此时无消费者**（G2 经 meta 交棒，不走 wire）→ **暂不产生重复** |
| **演进 = C**（共享核心库） | 通信/命令服务落地时，把 ①② **收敛为零 OSAL 依赖的共享核心库**：bootloader 用 osal-none 实例化、app 用 RTOS 实例化；**bootloader 侧不留第二实现**；boot 组作为命令组迁入服务（§5.1） |

- **共享核心按最严约束写**：零动态内存、零 OSAL、停等（R-DL-7）、单执行流（R-NFR-1）——**最严宿主定义核心，富裕宿主不改核心**。
- **先例**：mcumgr SMP——同一协议 + 同一 image 命令组，既跑 MCUboot serial recovery（引导侧极简传输），也跑 Zephyr app 的 mcumgr（多传输后端、全命令集）。"同一 wire、两个宿主"是成熟形态。
- **契约落点（2026-09-19 定）**：首版随 `lib/boot/include/`（与镜像头契约同处，**不预先新开层**）；该头须**纯线格式、不含 boot 语义**，使服务化时的迁移是"**搬家不改格式**"。app 侧在服务化前不 include 它。

### 3.12 布局的存储形态与布局指纹（2026-09-19）

**决议一：片内不预留"持久化分区表"区。**

| 诉求 | 需要片内持久化吗 | 现有手段 |
|---|---|---|
| 固件知道自己布局 | ❌ | **编译期常量**（现状，ADR-0024） |
| 上位机知道同一布局（算偏移/续传点） | ❌ | **同一张工程配置两侧投影**（§3.9） |
| 策略级几何约束被拦下 | ❌ | `_Static_assert` + 工具校验（缺口 #23，保护强度最高） |
| 设备**报告**布局（诊断） | ❌ | 后门诊断命令直接读编译期常量 |
| **改布局不用重烧固件** | **物理上不成立** | 布局决定链接基址/`payloadOffset`/槽容量 → 布局变则镜像必重链重烧，而重烧时顺手重烧表是免费的 |

**四条否决理由**：① 上表末行——flash 里的表**换不来任何独立性**；② **唯一事实源**——两份真源凭空新增失效模式（表坏了信谁：回退常量则表是摆设，拒绝启动则多一条 brick 路径）；③ 违背 K-40 的**保护强度降序**（把编译期能拦的事实挪到运行期读取 = 主动降级）；④ **容量**（一个 16K 扇区，而槽几何是整数扇区算好的）。**生态对照**：MCUboot 没有 flash 内分区表（编译期/devicetree），ESP-IDF 有（0x8000 分区表）——差别在**动机**：ESP 的分区偏移**不被编译器使用**、是运行期事实（app 按 label 查任意分区）；我们的槽偏移**同时被链接器使用**，故编译期才是它的正确位置。**形态像，位置不同。**

**决议二：加"布局指纹"（进 meta 的预留位）。**

- **要防的场景**：换了布局（换 Flash 规格 / 改槽几何）重烧 bootloader，而**旧 meta 还躺在片内**、带着 `VALID` + `activeSlot`——新布局下那个槽已不是原来的东西。
- **载体**：**meta entry 的 `flags` 高 16 位**（bit16..31）= 16-bit 布局指纹（几何 + 槽表 hash）；bit0 = 确认触发（既有）；bit1..15 保留。**entry 仍 32B，零容量成本**。
- **行为**：指纹不匹配 → 该份 meta 视为**不兼容**（等价失效）→ 走冷启动路径挑合法镜像，并按新指纹重写。
- **价值定位（诚实口径）**：它不是"否则会砖"的保险——**真正的兜底是镜像校验**（跳错地址 → 头部/摘要判定失败 → 不跳转 → 进后门）；指纹的价值是把**间接症状**（"镜像无效"）变成**显式判定**（"决策数据与当前布局不兼容"），与 R-SLOT-12（配置错误显式报错）同手法。
- **更强的候选（记待定）**：把 **32-bit 布局 ID 放进镜像头**，用来判"镜像是否为这套布局构建"——属**契约 v2 改动**，留到布局定稿时一并评估。

## 4. 提交策略矩阵

| 轴 | overwrite | swap | direct-xip | ram-load |
|---|---|---|---|---|
| 槽布局 | 运行槽 + staging（可同介质另区） | A/B 等大 + staging/scratch 语义 | A/B 均可 XIP | 非 XIP 槽 + RAM 目标 |
| 提交动作 | staging 全量覆盖运行槽 | 逐扇区对调（进度落 **meta 的追加进度区**，§5.2） | 只翻指针 | 校验后拷入 RAM 启动 |
| 写放大 | ~1×（一次升级） | 2-3× | ~1×（staging 一次） | 1× + RAM 搬运 |
| 回滚能力 | 无（旧镜像已覆盖） | 最强（掉电任意点可续/可退） | 靠启动计数回退（K-08） | 靠启动计数回退 |
| 掉电恢复点 | staging 未校验完 = 视为无效，重来 | 进度在 meta，断点续 | 指针未翻 = 旧镜像仍在 | 同 direct |
| 介质要求 | 任意 | 任意（搬移在 bootloader 语境，运行 app 已停） | 槽可 XIP + remap 支持 | 无 XIP 要求 |
| 启动时间 | 最短 | 最长（先搬移） | 短 | 中（拷贝） |
| 典型场景 | 快速升级、面积紧、可接受"坏则回 bootloader 收固件"（配后门 K-12） | 高可靠、不能丢旧版 | **竞赛双 bank 片内布局的自然选择** | 步骤 4 外部 flash 槽的候补 |

> 观察（MCUboot 取舍轴）：回滚能力 vs 写次数/面积/启动时间。**swap 的搬移成本没有换回竞赛场景的等价值**——手机场景需要"运行中自替换还可断电恢复"，竞赛场景升级由人触发、bootloader 语境提交即可，direct + 启动计数回退是量级更轻的同功能物。具体取舍拍板见 Q-01。
>
> **2026-09-18 补（几何，K-41）**：swap 落地取 **using-offset**（非 scratch / move）——副槽 = 主槽 + 1 扇区为**最优比**（等大亦合法），镜像写**副槽第 2 扇区起**，首扇区作"下行游标"缓冲区；要求**槽内扇区均一**。故上表 swap 行的"staging/scratch 语义"应读作"**副槽多一个游标扇区**"。

## 5.2 决策数据的两段式与副本份数（2026-09-18 收敛）

**已定（2026-09-18）**：

1. **份数 = 3 份**（不变式要求 ≥3 份，推演见下文；第三份归属在布局定稿时一并拍板）。
2. **两段式**：**决策区**（3 份 16K 副本，每份头部 32B entry，**整写式**）+ **提交进度区**（独立的 1 份已擦 16K，**追加式记录**）。

**为什么必须两段式**（物理约束，非优化）：两类信息的写入范式**互斥**——决策态要"擦-重写"（因其复用同一位置），进度要"只追加"（因其每次写新位置），**不可共处一个擦除单元**（同扇区内一个要擦掉重写就会连带毁掉另一个）。生态同构：MCUboot 的决策标志（`image_ok`/`copy_done`/`magic`）是"写一次/擦-写"型，而其 swap status 是**独立的追加记录区**（K-30/K-36/K-43）。

| | 决策 entry | 提交进度 |
|---|---|---|
| 更新形态 | 重写整条（历史无意义） | 只往后加（每步留痕） |
| 频率 | ~5 次/OTA 周期 | ≤14 条/次 swap（2 条/扇区，K-41） |
| 范式 | 整写式（读极简：校验一条） | 追加式（省擦、省耐久） |
| 若被强行统一 | 全追加 → 决策态变"扫日志"读取，且踩 retention 无厂商背书 | 全整写 → ≈3.1s 纯擦除自伤 |

**进度区生命周期**（与擦除纪律自洽）：引导期擦一次 → swap 期间追加 ≤14 条 → 提交完成/回退完成后擦回"已擦" → **终态即"已擦"**，与"至少一份已擦副本"的不变式天然一致；擦除次数 = 1 次/OTA，耐久可忽略。**归属**：进度区是**提交器的私有黑盒**——核心只提供"已擦容器 + 追加写纪律"，内容与解释权属策略（§3.7）。

**已定前提**：擦除归引导侧（Q-12）——写者只向"已擦副本"program，bootloader 在引导期恢复"至少一份已擦"的不变式。

**历史记录（2 份推演，保留备查——不变式撑不住）**：

| 步骤 | 谁 | 动作 | c1 | c2 |
|---|---|---|---|---|
| 稳态 | — | — | VALID·seq20 | 已擦 |
| ① 写 PENDING | app | program c2 | seq20 | PENDING·seq21 |
| ② 引导 | bootloader | 需已擦份 → 无 → 擦 c1 → program c1（计数 +1） | seq22 | seq21 |
| ②' 引导 | bootloader | 再擦 c2（非最新）腾出空位 | seq22 | 已擦 |
| ③ 写 CONFIRM | app（新槽） | program c2 | seq22 | VALID·seq23 |
| ④ 稳态 | — | 零写 | seq22 | seq23 |
| ⑤ **下一轮 PENDING** | app | **池中无已擦份可用** ✗ | — | — |

卡点在 ⑤：确认之后池中 0 份已擦，而下一轮 PENDING 发生在**任何 bootloader 运行之前**（设备持续运行中发起升级）。要重新腾出已擦份只剩三条路：**稳态启动期擦**（违反 R-SLOT-8 稳态零写、且烧寿命）／**app 自己擦**（即 ≈260ms stall，等于现状）／**多留一份**。

**3 份推演（不变式自持）**：bootloader 每次引导**只保留最新份有效、其余全部擦掉**（保底 2 份已擦）→ CONFIRM 消耗 1 份后仍余 1 份，正好接上下一轮 PENDING；稳态零写不破。

**落点收敛（2026-09-18）**：

| 区 | 归属 | 说明 |
|---|---|---|
| **决策区 3 份** | `meta` 32K（2 份）+ **bank2 头部 16K 空档 `0x10C000`**（第 3 份） | **已定（2026-09-19）**：日志分区**不再写入内部 flash**（改走外挂介质）→ 互斥解除，第三份**落此即定** |
| **提交进度区** | **`meta_resv` 16K** | 该 16K 原本就声明给"swap 进度/策略扩展"——现在进度区确认存在，**名副其实、无新增成本**（终态为"已擦"，不额外占容量） |
| ~~2 份方案~~ | — | **否决**：不变式撑不住（上表 ⑤ 卡点）；其代价是每周期一次应用侧 ≈260ms 擦除 |

**遗留要点**：① ~~第三份落点与"日志分区"候选地互斥~~ → **已定（2026-09-19）**：日志分区不再写入内部 flash，互斥解除，第三份落 `0x10C000`；② 未确认窗口内每次启动可能多 1–2 次擦（≈260ms/次）——**与 R-SLOT-8"稳态零写"不冲突**（只发生在未确认窗口，`state == VALID` 时零写）；③ 进度区的擦除/回收由引导期承担，与"擦除归引导侧"一体。
