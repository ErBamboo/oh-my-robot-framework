# 镜像头契约（提案 v0——待逐字段确认）

> **状态**：提案（2026-09-14）。逐字段确认后落为契约头（S2-1 交付物），并回写布局配置的语义说明。
>
> **约束锚点**：同目录 `reference_design_notes.md` 的 K-22/K-23/K-28（镜像头形态 / 独立对齐量 / 校验跨平台一致性）与 `multi_strategy_boot_design.md` 的 Q-04/Q-05；需求出处见 `boot_ota_requirements.md` 的 R-IMG-1..6。
>
> **契约地位**：本头是 bootloader 与 app **两个独立工程之间的 ABI**（ADR-0021 (boot_multi_strategy_skeleton)）。任何布局变更必须升 `hdr_version`，旧侧遇新侧结构**优雅拒绝**而非按旧布局误读。

---

## 1. 设计前提（已拍板，不在本提案讨论范围）

- 提交策略 direct-xip：槽 = A/B，均在片内、可 XIP；提交 = 翻决策指针，不搬移镜像。
- 镜像 = 自描述二进制；bootloader 只认镜像（不 care 来源与存储点）。
- 摘要算法可演进：头带算法 ID + **固定尺寸预留区**（CRC32 起步，SHA-256+ECDSA 演进不动契约）。
- canonical 摘要 = **CRC-32/ISO-HDLC**；芯片后端负责映射（F4 后端逐字变换后映射回该口径）。
- 头本体是**被摘要覆盖的只读元数据**；运行期可变状态（是否已确认、当前活动槽）一律放决策数据区，**不进镜像头**。

## 2. 槽内布局

```
槽基址（app_a 0x10000 / app_b 0x110000）
  +0x000  ┌──────────────────────────────┐
          │ OmImageHeader（固定 64B）     │  ┐
  +0x040  ├──────────────────────────────┤  ├─ 摘要覆盖 [0, digest_offset)
          │ 填充 → payload_offset         │  ┘
  +0x200  ├──────────────────────────────┤  ┐
          │ 负载（app 二进制）            │  ┘
          ├──────────────────────────────┤
          │ 摘要区（固定预留 256B）        │      ← 不参与自身摘要
          └──────────────────────────────┘
```

- **头在槽基址、负载在 `payload_offset`**：与 MCUboot 同构（其 `ih_hdr_size` 即负载偏移，典型 0x200 正是为满足向量表对齐）。
- 摘要覆盖「头 + 填充 + 负载」，**不覆盖自身**——与 MCUboot、ESP-IDF 一致，无循环。

## 3. 头字段表（拟定形态）

```c
typedef struct OmImageHeader {
    uint32_t magic;              /*  0 */
    uint16_t hdr_version;        /*  4 */
    uint16_t hdr_size;           /*  6 */
    uint32_t payload_offset;     /*  8 */
    uint32_t image_size;         /* 12 */
    uint32_t image_total_size;   /* 16 */
    uint32_t image_version;      /* 20 */
    uint32_t flags;              /* 24 */
    uint16_t digest_algo;        /* 28 */
    uint16_t digest_len;         /* 30 */
    uint32_t digest_offset;      /* 32 */
    uint16_t digest_region_size; /* 36 */
    uint16_t flags_reserved;     /* 38 */
    uint32_t header_crc32;       /* 40 */
    uint8_t  reserved[20];       /* 44 */
} OmImageHeader;                 /* = 64B，全字段自然对齐 */
```

| # | 字段 | 宽度 | 偏移 | 取值 | 说明 |
|---|---|---|---|---|---|
| 1 | `magic` | u32 | 0 | 常量（见 IH-01） | 唯一「这是本框架镜像」判据；**取非 `0xFFFFFFFF`／非 `0x00000000` 值**，使空白/擦除 flash 自然不匹配 |
| 2 | `hdr_version` | u16 | 4 | 常量，头布局**不兼容**变更时 +1 | 旧侧遇新结构在此拒绝（见 §6 第 3 步）。此字段是相对 MCUboot 的增强——MCUboot 无结构版本字段，只能靠换 magic 表达不兼容 |
| 3 | `hdr_size` | u16 | 6 | `sizeof(OmImageHeader)` | 头本体字节数。**语义严格 = 结构体长度，不等于负载偏移**——与 MCUboot 的 `ih_hdr_size` 语义**刻意分离**，避免"头大小"与"负载偏移"两个概念混用 |
| 4 | `payload_offset` | u32 | 8 | 构建期常量 | 负载相对槽基址的偏移；**必须等于 app 链接偏移**，且须满足向量表对齐（见 IH-03） |
| 5 | `image_size` | u32 | 12 | 构建期 | 负载纯长度，**不含头、不含摘要区**（"不含"是契约要点） |
| 6 | `image_total_size` | u32 | 16 | `payload_offset + image_size + digest_region_size` | 冗余但**防歧义**：一次比较即可判"是否越出槽容量" |
| 7 | `image_version` | u32 | 20 | 构建期 | 回滚与升级判定（见 IH-04） |
| 8 | `flags` | u32 | 24 | 构建期 | 见 §4；位值**刻意不连续**，留空洞 |
| 9 | `digest_algo` | u16 | 28 | 构建期枚举 | 演进核心：旧侧读到未知值 → 拒绝该槽（见 IH-08） |
| 10 | `digest_len` | u16 | 30 | 构建期 | 显式写死长度，**不靠算法隐式推导**，便于旧侧在未知算法时安全跳过 |
| 11 | `digest_offset` | u32 | 32 | `payload_offset + image_size` | 摘要区起点。**显式给出而非隐含计算**，为将来"摘要挪到决策数据区"留路 |
| 12 | `digest_region_size` | u16 | 36 | 常量 | 摘要区**预留容量**（非已用长度）；旧侧读到比自己大的值 → 拒绝 |
| 13 | `flags_reserved` | u16 | 38 | 恒 0 | 与 `flags` 的空洞配合 |
| 14 | `header_crc32` | u32 | 40 | 见 IH-07 | 头自身完整性；启用时计算需将本字段清零（U-Boot `hcrc` 范式） |
| 15 | `reserved[20]` | 20B | 44 | 恒 `0xFF` | 凑齐 64B 并为**兼容性加字段**留空间（不兼容变更走 `hdr_version`）。若 IH-09 采用「头内槽绑定字段」方案，则从本区划出 2B 作 `slot_id`（头仍为 64B，不涉及版本演进） |

合计 **64 字节**；全部字段自然对齐（无跨边界访问）。

## 4. flags 位分配

| 位 | 宏 | 含义 |
|---|---|---|
| `0x00000001` | `OM_IMAGE_F_NON_BOOTABLE` | 不可直接启动（为将来的资源镜像/从镜像预留） |
| `0x00000100` | `OM_IMAGE_F_SLOT_BOUND` | 镜像已按某个槽地址构建（见 IH-09） |
| `0x00000200` | `OM_IMAGE_F_DIGEST_IN_META` | 摘要存决策数据区而非槽内尾部（为搬家预留） |
| `0x00010000+` | 厂商/项目私有区间 | — |

**明确不放入头的**：`CONFIRMED` / `ACTIVE` 等运行期可变状态——头被摘要覆盖，改写头会破坏摘要；这类状态属决策数据区（与 MCUboot、ESP-IDF 把可变状态放 trailer/otadata 的做法一致）。

## 5. 摘要与摘要区

- **覆盖范围**：`[0, digest_offset)` = 头 + 填充 + 负载。
- **摘要区**：固定预留 256B（装 SHA-256 + ECDSA-P256 签名 + 公钥/密钥哈希有余）；预留容量恒定 → **新旧两侧无需重新协商布局**。
- **两处硬约束**（来自 canonical 变体在目标芯片上的实现方式）：
  1. 摘要覆盖区须 **4 字节对齐且长度为 4 的倍数** → `payload_offset` 与 `image_size` 均须 4 字节对齐（生成工具保证）；
  2. **填充区在摘要覆盖范围内**，其取值必须确定（提案 `0xFF`，与擦除态一致）——否则同一镜像在不同工具下摘要不同。

## 6. 优雅拒绝顺序（契约的一部分）

```
1. 读满头（读失败 → 该槽不可用）
2. magic 不符                    → 拒绝（含"空白槽"语义）
3. hdr_version 不符              → 拒绝（区分"太老/太新"）
4. hdr_size != sizeof(...)       → 拒绝（冗余双重确认）
5. flags 含 NON_BOOTABLE         → 拒绝
6. 四个尺寸字段范围自洽（溢出安全加法）
   且 image_total_size <= 槽容量 → 否则拒绝
7. payload_offset 对齐且 >= hdr_size → 否则拒绝
8. digest_algo 未知              → 拒绝（不尝试用未知算法校验）
9. digest_len 与算法不符         → 拒绝
10. 按算法计算 [0, digest_offset) 摘要并与摘要区比对 → 不符则拒绝
```

**第 6 步必须先于任何基于头内尺寸的访问**——此刻头尚未被认证。拒绝后的动作：标记该槽不可用 → 试另一槽 → 全不可用则进入交互（后门）状态；**不搬移、不擦除**。

## 7. 待确认清单

### 7.1 需要你选择的（有备选）

| 编号 | 待确认点 | 提案 | 备选 / 影响 |
|---|---|---|---|
| **IH-01** | `magic` 取值 | `0x4F4D5249`（ASCII "OMRI"） | 其他四字码。**一旦发布不可更改**（所有已烧录镜像都带它） |
| **IH-02** | 头整体尺寸 | 64B | 128B（更多预留/更多填充）。64B 与 cache line 友好，且现有预留已够加字段 |
| **IH-03** | `payload_offset` 取值 | `0x200`（512B，= 目标芯片向量表对齐下限） | **连带确认**：app 链接基址 = 槽基址 + `payload_offset`，即 **0x10200 / 0x110200**；这与布局表里 `app_a@0x10000` 是"槽基址"的语义必须写清（见 §8）。备选更大值（如 0x400）无收益 |
| **IH-04** | `image_version` 编码 | 单 u32 = `major<<24 \| minor<<16 \| patch<<8` | MCUboot 式 8B 四段（多一个 `build_num`）。单 u32 省 4 字节；若将来需要构建号，可借 `reserved` 扩展 |
| **IH-05** | 摘要区位置与尺寸 | 槽内**负载之后**，固定 256B | 备选：头后负载前（MCUboot TLV 式，便于将来加多类 TLV，但需引入 TLV 解析）。位置一旦发布不可改 |
| **IH-06** | 填充区取值与是否入摘要 | 填充 = `0xFF`，**纳入**摘要 | 若填充不入摘要，摘要须分两段计算（复杂化）；纳入则要求填充值确定 |
| **IH-07** | `header_crc32` 是否启用 | **不启用**：字段保留、生成时置零 | 不启用的理由：direct-xip 下活动槽头永不重写 → "半写头"路径不存在；且头已被整镜像摘要覆盖，头 CRC 无认证能力、不能替代摘要。启用不改契约（仅生成器与 bootloader 各加一段 64B CRC）。**若实测发现"全镜像摘要之前的快速空槽判定"不足，再启用** |
| **IH-08** | `digest_algo` 枚举命名 | 显式命名 canonical 变体：`0=NONE, 1=CRC32_ISO_HDLC, 2=SHA256` | **禁用裸名 "CRC32"**——芯片后端实现口径不同（目标芯片硬件原生形态与 canonical 不同源），算法 ID 必须命名 canonical 变体而非某个后端的口径 |
| **IH-09** | 槽绑定的表达与校验 | 两者都做：① 从 `reserved` 划出 2B 作 `slot_id`（构建期写入，bootloader 比对）+ `OM_IMAGE_F_SLOT_BOUND` 置位表示"已绑定"；② bootloader 校验负载向量表里的初始栈指针/复位地址落在本槽区间 | 备选：只做 ②（零契约字段，但依赖对负载格式的假设）或只做 ①（便宜直白，但不验证负载真伪）。**direct-xip 下 A/B 是两个不同二进制，把 A 的镜像提交到 B 槽必然跑不起来**，故这层保护不可省 |
| **IH-10** | 镜像生成工具形态 | 主机侧工具（脚本语言）产出"头 + 填充 + 负载 + 摘要区"的完整镜像，并回读校验；构建系统侧包一个任务钩子 | 备选：手工/外部工具（无）= 无法保证摘要一致性，不推荐。**这是 S2-1 的另一半交付物** |

## 8. 与既有配置的联动

- **布局表语义补充**：`om_bootcfg.h.example` 中 `app_a@0x10000` / `app_b@0x110000` 是**槽基址**；app 的链接基址 = 槽基址 + `payload_offset`。该说明需回写进模板注释。
- **有效镜像容量** = 槽大小 − `payload_offset` − 摘要区预留；bootloader 的越界校验以此为准，槽大小取自分区表。
- **槽基址对齐**：`payload_offset` 为 0x200 时，两槽基址均须 0x200 对齐（现有 0x10000 / 0x110000 满足）。

## 9. 首版明确排除

bootloader 自身镜像化（引导区自升级）· 镜像加密 · 镜像压缩 · 多镜像（一次升级携带多个可启动单元）· TLV 式可扩展区 · 签名链（SHA-256+ECDSA 为演进档，契约已留位）。
