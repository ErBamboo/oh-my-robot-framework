# Boot 模块对象与目录约定

本文约定 boot 模块中类型与头文件的归属判定，以及 Image / Meta / Verifier 的职责边界。新增类型或调整目录时以此为准。

## 核心原则

按“真相归属与兼容边界”分类，不按“看起来是不是纯数据”分类：

1. 会被写进存储，或必须被两个独立编译的产物按同一字节布局解释的数据，属于契约。
2. 只通过对象公开接口交换、不落盘、没有资源和生命周期的数据，属于值对象。
3. 有身份、持有资源、带生命周期操作的类型，属于对象。
4. 只为实现对象而存在的策略或协议，属于内部组件，不单独成为数据层或对象层。

## 判定顺序

对新类型依次回答：

| 问题 | 归属 |
| --- | --- |
| 改了它，已烧录的镜像或已写下的记录会被读错吗？ | `contract/` |
| 它只是公开 API 收发、可复制、无资源的值吗？ | `*_data.h` |
| 它持有句柄/偏移/引用，并有 init/read/write/verify 等生命周期吗？ | 对象头 |
| 它只是实现对象所需的策略/协议，没有独立身份吗？ | 对象旁的内部组件头，或留在 `.c` |

四问都不满足的类型不对外暴露，保留在实现文件内。

## 四类归属

### `contract/`

定义跨产物共享的字节真相：字段偏移、魔数、版本、flags 位布局、持久化枚举数值。

判据：修改后是否需要同时更新打包工具、引导方、应用或上位机，且旧产物可能无法兼容。

典型符号：

- `OmImageHeader`：镜像文件格式。
- `OmBootMetaEntry`：启动状态记录布局。
- `OmBootMetaState`、`OmBootMetaReason`：数值写入记录，属于持久化语义。
- `OM_BOOT_META_FLAG_*`、`OM_IMAGE_SLOT_*`、`OM_BOOT_SLOT_COUNT`：共享位布局与身份。

契约头只做定义，不依赖对象、驱动或 OS。

### `*_data.h`

定义对象公开接口的内存值词汇：解码后的记录、读取结论、校验结论、诊断描述。

判据：调用方会复制、比较或打印它；它不拥有资源，也不决定落盘格式；其布局变化不影响旧镜像或旧记录。

典型符号：

- `OmBootMetaData`、`OmBootMetaReadStatus`、`OmBootMetaReadResult`。
- `OmBootImageStatus`、`OmBootImageInfo`、`OmBootImageResult`。

值对象可以引用契约类型，例如 `OmBootMetaData` 中的 `OmBootMetaState`，但不得在值对象中重复定义持久化枚举或位布局。

读取/校验结果按“一个 tag + 一组整体有效的 payload”组织：

- `OmBootMetaReadResult`：`status` 是唯一 tag，`record` 是载荷；`record` 仅在 `OM_BOOT_META_READ_OK` 时整体有效。
- `OmBootImageResult`：`status` 是唯一 tag，`info` 是载荷；`info` 仅在 `OM_BOOT_IMAGE_VALID` 时整体有效。失败诊断只使用 `status`，不复用 `info` 作部分有效的快照。

不要把多个正交维度拍进同一个结果，也不要用一个 tag 门控部分有效的字段；需要多个维度时拆成嵌套值或独立结果。

### 对象头

对象是身份、资源和行为的聚合。判据：调用方是否跨多次调用持有它；它是否拥有分区句柄、副本偏移、校验器引用等资源。

- `OmBootImage`：镜像分区、槽身份、校验器引用，提供构造、校验和只读访问。
- `OmBootMeta`：meta 分区、副本偏移与大小，提供读取、写入、清理。

对象头负责在契约字节与值对象之间翻译。它不应该把 32 字节记录或原始镜像头直接暴露给调用方。

### 内部组件头

内部组件有实现协议或策略，但没有独立身份和生命周期。放在对象旁边，不进入契约层或值对象层。

`OmBootImageVerifier` 属于此类：它持有校验算法表，执行“读头、校验槽绑定、流式摘要、比对”的完整协议。它不持分区，不落盘，也不作为普通 API 结果值。

## Meta 与 Image 的枚举归属

`OmBootMetaState` 与 `OmBootMetaReason` 放在契约层，因为它们的数值直接写入 `OmBootMetaEntry.state/reason`。改变数值会改变旧记录的语义。

`OmBootImageStatus`、`OmBootImageInfo`、`OmBootImageResult` 放在 `image_data.h`，因为它们是本次校验的运行期输出，从不写入存储。`OmBootImageInfo` 虽然与镜像头字段相似，但它是给调用方的解码子集，不是镜像文件 ABI。

因此两者不是重复结构，而是生命周期不同：一个描述持久化真相，一个描述运行期结论。将来若镜像头增加持久化的状态或原因字段，那组值应进入契约层。

## 校验器的定位与扩展

`OmBootImageVerifier` 是可注入的校验策略，保留独立类型，用于以下扩展场景：

- 新增摘要算法：实现 `begin/update/finish` 并注册一条 `OmBootImageVerifyAlgorithm` 描述符。
- 硬件校验：回调内部调用硬件摘要引擎，接口仍保持算法描述符。
- 产品自定义策略：构造自己的算法表，初始化校验器后交给 Image 使用。

约束：

- 算法标识必须与镜像头 `digestAlgo` 的取值一致。
- 摘要长度不得超过摘要区容量。
- 算法表与校验器必须比使用它的 Image 活得久。
- 描述符的 context 由实现方持有；框架只透传指针，不分配、不对齐、不校验其内容。上下文的大小、对齐、生命周期和并发策略由实现方负责。

`OmBootImage` 持有校验器指针而不是内嵌对象，便于多个 Image 共享同一校验器；算法上下文由校验器实现方持有，使静态对象、硬件句柄或寄存器块都可以直接作为 context。

## 依赖方向

- 契约头不依赖对象、驱动或 OS。
- 值对象头可以依赖契约头。
- 对象头可以依赖契约头、值对象头和资源头。
- 内部组件头只依赖值对象、资源与算法接口。
- 实现文件包含自己实际使用的头，不依赖其他头文件的传递包含。

依赖只能从上往下，不能由契约反向依赖对象，也不能由值对象反向依赖对象。

## 常见错误

- 把运行期状态枚举放进契约层，导致运行期语义被误认为落盘 ABI。
- 在值对象里重新定义持久化枚举或 flags，形成第二份真相。
- 对象 API 直接返回原始记录或原始镜像头，泄漏布局细节。
- 让值对象持有分区句柄或其它资源。
- 为“转发”而造对象；只做字段搬运、没有资源或行为的类型应留在实现文件内。
